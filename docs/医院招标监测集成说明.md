# 医院招标监测集成

医院招标监测由森特智行内置的一次性采集任务负责读取公开采购来源并生成脱敏快照；运行前会把当前客户的名称、地区、需求和摘要派生词写入一次性私有临时配置，采集完成后由森特智行再用同一份客户表重新计算关联、审计运行并展示结果。采集器运行时随主后端发布，不要求最终使用者填写同步 URL、Token 或接入第三方 API。

## 数据边界

- 两个项目不共享 SQLite、运行时目录、PushPlus 凭据或原始抓取响应。
- 同步快照只允许 `hospital-tender-snapshot-v1` 契约中的公告、来源健康和运行摘要字段；`rawContent`、请求头、Token、文件路径和数据库字段会被拒绝。
- 客户匹配只使用同步时由森特智行生成的客户快照（名称、地区、需求和摘要派生词）；不会自动修改客户、商机、动作、风险或销售阶段。
- 公告类型会将采集器的计划、采购、变更、结果、`terminated`（废标/终止）和合同词汇映射为可筛选的系统枚举。
- 采集器机器身份只能访问 `POST /api/integrations/hospital-tenders/sync` 和 `GET /api/integrations/hospital-tenders/health`，不能读取客户或其他业务接口。

## 森特智行接口

生产环境默认每 60 分钟自动执行一次轮巡，每批按稳定客户 ID 处理 10 个客户。每个轮次只抓取一次公开来源并把脱敏快照暂存在 SQLite；后续小时复用同一快照推进客户游标，避免每批重复访问公告网站。只有整批成功才推进游标，部分入库或通知失败都会保留当前批次。服务重启后从持久化游标继续；已删除客户不会重放，本轮游标之前新增的客户会在下一轮纳入，全部客户删除时会安全结束当前快照。轮巡状态、批次运行记录、快照和数据库租约分别持久化，进程内定时器和数据库锁共同防止重叠运行。

登录用户可通过医院招标页面的“立即检测下一批”按钮调用 `POST /api/hospital-tenders/scheduler/run-next`。该入口只接受空请求体，受登录会话和 CSRF 保护；机器身份不能调用。`GET /api/hospital-tenders/scheduler` 返回安全的轮巡状态和最近批次，不包含原始抓取 payload。旧的 `POST /api/hospital-tenders/run` 仍保留用于一次性全量人工诊断，不替代自动批次游标。采集子进程只继承最小运行环境，不会继承同步地址、Bearer、PushPlus 或模型凭据；失败时不会接收快照。运行时位于后端 `backend/vendor/hospital-tender-monitor`，需要部署环境提供 Python 3.11+，`HOSPITAL_TENDER_PYTHON` 必须指向规范化、非符号链接、无 setuid/setgid 与文件 capability 的绝对路径，且文件及各级目录不能由后端服务账号改写。

自动轮巡配置：

- `HOSPITAL_TENDER_AUTO_RUN`：生产默认开启，开发默认关闭；
- `HOSPITAL_TENDER_INTERVAL_MINUTES`：默认 `60`；
- `HOSPITAL_TENDER_BATCH_SIZE`：默认 `10`。
- `HOSPITAL_TENDER_PUSHPLUS_TOKEN`：开发环境可缺省；缺省时仍采集和入库，但 `/api/hospital-tenders/scheduler` 与 `/api/hospital-tenders/health` 会明确返回 `notification.status=disabled`，不会把通知能力报告为已启用。生产自动轮巡开启时，preflight 要求该变量存在、至少 32 个安全字符且不复用其他项目凭据；Token 只由后端读取。

`0016` 迁移会在 SQLite 中持久化固定的 `60/10` 默认状态。环境变量同时作为发布合同和持久化值缺失或无效时的回退，不会覆盖已经存在的 scheduler 状态。如需使用非默认间隔或批量，由已登录用户通过受 CSRF 保护的 `PATCH /api/hospital-tenders/scheduler` 提交 `intervalMinutes` 和/或 `batchSize`，将新值持久化到 SQLite。服务重启会继续使用该持久化状态，不会重置当前轮次。

普通登录会话可访问以下接口（写操作需要 CSRF）：

- `GET /api/hospital-tenders`
- `GET /api/hospital-tenders/:id`
- `GET /api/hospital-tenders/summary`
- `GET /api/hospital-tenders/sources`
- `GET /api/hospital-tenders/health`
- `GET /api/hospital-tenders/scheduler`
- `GET /api/hospital-tenders/scheduler/runs`
- `PATCH /api/hospital-tenders/scheduler`（需要 CSRF，持久化轮巡配置）
- `POST /api/hospital-tenders/scheduler/run-next`（需要 CSRF）

旧的机器同步入口仍保留用于隔离迁移窗口：采集器同步身份使用独立的 `HOSPITAL_TENDER_SYNC_TOKEN`。生产环境若启用该入口，令牌必须是独立的高熵值，不能复用会话、微信或助手密钥；令牌只放在受保护的后端/采集器环境文件中。新部署不需要配置它。

## 独立采集器桥接

独立项目 `hospital-it-tender-monitor` 的本地实现提交为 `a5d32216953cbd43f39b09ae50cade54e9d07090`。它新增：

- `export-snapshot --output <受保护路径>`：导出不含原始正文和凭据的快照；
- `sync --endpoint <森特智行同步地址>`：发送已有快照；
- `run-and-sync`：采集成功后强制发送；
- `run-and-sync-if-configured`：systemd oneshot 使用，未配置同步地址/令牌时仍完成本地采集，不会伪造同步成功。

采集器环境变量：

```text
SENTELLIGENT_HOSPITAL_TENDER_SYNC_URL=
HOSPITAL_TENDER_SYNC_TOKEN=
```

同步地址使用 HTTPS；仅本机回环调试允许 HTTP。森特智行后端对应环境变量为 `HOSPITAL_TENDER_SYNC_TOKEN` 和可选的 `HOSPITAL_TENDER_SYNC_OWNER`。

## 页面

前端一级导航“医院招标监测”提供自动轮巡状态、当前轮次、每批客户数、轮次进度、最近完成时间、下次运行时间、安全错误、立即检测下一批、公告筛选、公告详情、原文链接和来源健康。公告和匹配结果仍是只读视图，任何后续跟进通过客户/商机原有人工确认流程完成。

## 验收顺序

1. 本地运行独立采集器测试和 `compileall`。
2. 本地森特智行运行招标 focused API/契约测试、后端全量测试和前端构建/本地 QA。
3. 在明确的隔离或生产授权窗口内，先验证同步身份和来源健康，再观察公告匹配；不要把同步快照当作生产客户数据备份。
4. 阶段性版本须绑定单一 Git commit、迁移版本 `0016`、前端构建和 secret scan 证据后，才进入 GitHub 私有仓库/生产发布流程。
