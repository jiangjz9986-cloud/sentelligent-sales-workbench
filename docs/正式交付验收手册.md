# 森特智行 AI 销售作战台正式交付验收手册

更新时间：2026-07-19

## 1. 交付范围

本项目当前交付的是可运行 MVP：React 前端、Node 后端、SQLite 数据库、本地开发脚本、WSL 生产栈脚本、DeepSeek 后端模型接入、审计日志和自动化 QA 验收脚本。

当前业务访问地址：

- 前端业务地址：http://127.0.0.1:5184
- 后端接口地址：http://127.0.0.1:8897

核心业务闭环：

- 战情总览：进入客户、商机、快速记录、行动、风险、知识库和周报。
- 快速记录：支持文本和语音转写入口，默认新增记录为空；历史记录可载入已有分析并允许人工修改。
- 客户画像：先看客户列表，点击查看详情后进入客户维护界面；新增客户直接进入空表单。
- 商机档案：先看商机列表，点击查看详情后进入商机维护界面；新增商机直接进入空表单。
- 下一步行动、风险识别、知识库、商机看板和周报：均应支持列表搜索、详情查看、状态更新或内容生成。
- AI 能力必须只在后端调用，前端不保存、不展示、不构建任何模型密钥。

```powershell

```

`npm run dev:status` 应确认：

- aiAnalysisMode 为 model。
- modelProvider 为 deepseek。
- modelName 为 deepseek-v4-flash，对外交付名称为 DeepSeek-V4-Flash。

```powershell

```

## 3. 后端模型与密钥边界

模型密钥只允许放在 backend .env。不要写入前端源码、构建产物、截图、文档、周报、提交说明或日志。

后端模型配置边界：

- DeepSeek-V4-Flash 通过后端 OpenAI-compatible chat completions 调用。
- 健康检查只允许暴露模型模式、供应商、模型名和 ready 状态。
- 任何接口响应不得返回 provider key、Authorization header 或原始密钥片段。
- 自动化测试默认使用 mock 或受控环境，避免消耗正式模型额度。

密钥扫描：

```powershell
npm run scan:secrets
```

## 4. 审计日志

后端应记录关键写操作和 AI 触发动作，便于后续追溯：

- 客户新增、修改。
- 商机新增、修改。
- 快速记录分析、确认、同步客户或商机、进入周报。
- 周报草稿生成。
- 方案草稿生成。
- 风险状态更新。
- 知识库新增、修改。

审计接口：

```text
GET /api/audit-logs
```

验收时可访问：

```powershell
Invoke-RestMethod http://127.0.0.1:8897/api/audit-logs
```

审计记录不应包含模型密钥、完整请求头或敏感环境变量。

## 9. Phase 1 生产认证迁移

上线前先在受控终端生成密码哈希。密码只从标准输入读取，不得作为命令行参数、环境变量明文或文档内容出现：

```powershell
npm --prefix backend run auth:hash
```

将输出的 scrypt 哈希写入生产环境的 `AUTH_PASSWORD_HASH`，并完成以下生产配置：

```text
NODE_ENV=production
AUTH_ACCOUNT=<正式账号>
AUTH_PASSWORD_HASH=<auth:hash 输出>
AUTH_SESSION_SECRET=<独立生成的高强度随机值>
AUTH_COOKIE_SECURE=true
CORS_ALLOWED_ORIGINS=https://<正式业务域名>
```

迁移要求：

- 生产环境删除兼容用的明文 `AUTH_PASSWORD`，缺少哈希、会话密钥、Secure Cookie 或明确 CORS 来源时必须启动失败。
- `AUTH_SESSION_SECRET` 与模型密钥分开保存，轮换前先安排所有现有会话重新登录。
- 登录响应只创建七天有效的 `HttpOnly`、`Secure`、`SameSite=Lax` Cookie，前端存储中不保存会话值或 CSRF 值。
- 浏览器写操作必须携带 `X-CSRF-Token`；用户接口不得使用 `Authorization: Bearer`。
- 周报导出允许 `?format=word`，但 URL 不得包含 `query token`、授权值或会话值。
- `CORS_ALLOWED_ORIGINS` 只列正式 HTTPS 来源，不使用通配符，不把开发地址带入生产配置。

## 10. 数据库检查、备份与恢复

升级前先停止本项目服务并确认数据库离线。只允许停止 `sentelligent` 项目所属服务，不得结束机器上的全部 Node 进程。

```powershell
npm run wsl:stack:stop
npm --prefix backend run db:check
npm run wsl:db:info
npm run wsl:db:backup -- --label=phase1-complete
```

必须归档以下证据：

- `db:check` 与 `wsl:db:info` 均为 ready。
- `PRAGMA quick_check` 返回 `ok`。
- `PRAGMA foreign_key_check` 返回零行。
- 12 张既有业务表的记录数，以及 `schema_migrations` 中每个版本和 checksum。
- 备份文件绝对路径、字节数和 `SHA-256`；可在 WSL 使用 `sha256sum <备份路径>` 复核。
- 备份文件不进入 Git，不与 `.env`、日志或会话 Cookie 一起归档。

先对独立临时数据库做恢复演练，禁止直接覆盖在线数据库：

```powershell
npm run wsl:db:restore -- --database-url=/tmp/sentelligent-phase1-restore-test.sqlite --backup-path=<备份绝对路径>
npm run wsl:db:info -- --database-url=/tmp/sentelligent-phase1-restore-test.sqlite
```

恢复演练必须再次通过 `PRAGMA quick_check`、`PRAGMA foreign_key_check`、12 张业务表计数和迁移 checksum 比对。正式恢复时先停止本项目后端，确认无 `-wal`、`-shm` 或打开连接，再执行：

```powershell
npm run wsl:db:restore -- --backup-path=<已验真的备份绝对路径>
npm run wsl:db:info
npm run wsl:stack:start
npm run wsl:stack:health
```

恢复过程会先验证候选库，再原子替换并保留恢复前副本；任何校验失败都不得替换现有数据库。

## 11. Cookie、CSRF 与 CORS 验收

本地浏览器集成 QA 使用随机端口，并仅对该回环进程设置 `AUTH_COOKIE_SECURE=false`、`NODE_ENV=test` 和精确的 `CORS_ALLOWED_ORIGINS`。生产始终保持 `AUTH_COOKIE_SECURE=true`。

验收证据必须同时证明：

- 登录响应有七天 `HttpOnly` Cookie，响应体和浏览器存储都没有 Bearer token。
- 刷新页面通过 `GET /api/auth/session` 恢复登录，不依赖 localStorage。
- `POST`、`PATCH`、`DELETE` 请求有 `X-CSRF-Token`，没有 `Authorization` 请求头。
- 周报导出由带 Cookie 的 fetch 完成，URL 没有 query token。
- 退出调用 `POST /api/auth/logout`；旧 Cookie 再访问会得到 401，受保护界面回到登录页。
- 只有 `CORS_ALLOWED_ORIGINS` 中的来源获得 credentialed CORS 响应。

执行：

```powershell
npm --prefix outputs/product-design-prototype run qa:integration
```

## 12. 服务归属与应用回滚

所有服务单元、PID 文件、运行目录和日志目录必须带 `sentelligent` 项目标识。操作前先确认实际服务名和命令行归属：

```bash
systemctl list-unit-files 'sentelligent*'
systemctl status sentelligent-backend.service sentelligent-frontend.service
systemctl status sentelligent-caddy.service sentelligent-weixin-agent.service
```

禁止按进程名批量结束全部 Node、停止整台主机的容器栈或重启无关 systemd 服务。本项目脚本只可根据已记录 PID，并在命令行、工作目录和运行时指纹匹配后终止进程。

应用回滚步骤：

1. 只停止 `sentelligent-*` 项目服务，保留当前 release 目录、数据库备份及其 SHA-256。
2. 将应用 release 指针切换到上一已验收版本，不修改或删除已经执行的迁移记录。
3. Phase 1 数据库迁移采用加法迁移；回滚前确认旧应用能忽略新增表和新增列，不能兼容时停止回滚并使用向前修复。
4. 启动项目专属服务，执行健康检查、登录、查询、写入、周报导出和审计抽查。
5. 只有在应用回滚仍无法恢复且已完成恢复演练时，才按第 10 节离线恢复数据库。

数据库 schema 不做破坏性回滚。应用回滚与数据恢复是两个独立审批动作，不能在同一条自动命令中隐式完成。

## 13. 便携发布包

发布包必须从已经提交且工作树干净的发布候选分支生成。先完成前端生产构建和发布专项测试：

```powershell
npm --prefix outputs/product-design-prototype run build
npm run test:release
npm run release:package -- --output-dir=.runtime/releases
```

`release:package` 是本地离线脚本，不连接服务器、不读取生产环境文件，也不执行部署。默认生成标准 `tar.gz`，并在命令输出中给出归档绝对路径和归档 SHA-256。归档根目录内的 `release-manifest.json` 必须包含：

- 当前 Git branch、完整 commit 和工作树 clean 状态。
- `outputs/product-design-prototype/dist` 每个构建文件的 SHA-256。
- `backend/src/db/migrations` 每个迁移文件的 SHA-256。
- 生产必需环境变量名称，不包含任何变量值。
- 仅切换项目 release 指针的应用回滚步骤，以及数据库只允许前向迁移的边界。

发布包强制排除：

- `.env` 和生产环境文件；仅保留不含值的 `*.env.example`。
- SQLite 数据库、`-wal`、`-shm`、日志、PID 和会话目录。
- `node_modules`、包缓存、coverage 和临时目录。
- `.git`、`.codex`、`.runtime`、`.worktrees` 和代理运行元数据。
- 私钥、证书和已有压缩归档。

生成后必须解压到独立临时目录验证，不得直接覆盖当前项目：

```powershell
$archive = (Get-ChildItem .runtime\releases\*.tar.gz | Sort-Object LastWriteTime -Descending | Select-Object -First 1).FullName
$extract = Join-Path $env:TEMP "sentelligent-release-verify"
New-Item -ItemType Directory -Force $extract | Out-Null
tar -xzf $archive -C $extract
Get-ChildItem $extract -Recurse -Force
```

核对 manifest 的 branch、commit 与 `git branch --show-current`、`git rev-parse HEAD` 一致，并复算归档、构建和迁移 checksum。测试会在系统临时目录中自动生成并实际解压一个 fixture 归档，证明格式可以在 Windows 和 Linux 的标准 `tar` 中读取。

## 14. 生产预检

生产预检只读取事先准备的环境快照、离线数据库、备份和服务保护计划，不发起 SSH、HTTP、模型调用或 `systemctl`，也不会修改数据库和服务。运行环境必须为 Node.js 24 或更高版本。

在受控目录准备不进入 Git 的生产 `.env`，至少确认：

```text
NODE_ENV=production
AUTH_REQUIRED=true
AUTH_ACCOUNT=<正式账号>
AUTH_PASSWORD_HASH=<auth:hash 输出>
AUTH_SESSION_SECRET=<独立生成的至少 32 字节 base64url 值>
AUTH_COOKIE_SECURE=true
CORS_ALLOWED_ORIGINS=https://sales.example.com
SOLUTION_WRITES_ENABLED=false
```

`CORS_ALLOWED_ORIGINS` 必须是精确 HTTPS origin，不含路径、通配符、开发地址或额外来源。正式地址即使部署在 `/sentelligent/`，origin 仍只填写协议、主机和端口。

服务保护计划使用 JSON，所有实际变更目标必须属于四个项目服务；无关服务必须先登记为 `protected`，且不能出现在计划动作中：

```json
{
  "projectServices": [
    { "name": "sentelligent-backend.service", "enabled": true, "active": true },
    { "name": "sentelligent-frontend.service", "enabled": true, "active": true },
    { "name": "sentelligent-caddy.service", "enabled": true, "active": true },
    { "name": "sentelligent-weixin-agent.service", "enabled": true, "active": true }
  ],
  "unrelatedServices": [
    { "name": "account-vault.service", "protected": true, "active": true },
    { "name": "qingyang.service", "protected": true, "active": true },
    { "name": "proxy.service", "protected": true, "active": true }
  ],
  "plannedActions": [
    { "action": "restart", "service": "sentelligent-backend.service" }
  ],
  "plannedCommands": [
    "systemctl restart sentelligent-backend.service"
  ]
}
```

将服务名替换为服务器实际盘点结果，但不要把任何无关服务改名伪装成项目服务。预检禁止 `pkill`、`killall`、批量结束 Node、停止整套 Compose 栈，以及对非 `sentelligent-*` 单元执行 start、stop、restart、enable 或 disable。

执行：

```powershell
npm run preflight:production -- `
  --env-file=<生产环境快照路径> `
  --database=<离线数据库路径> `
  --backup=<新备份路径> `
  --backup-sha256=<事先记录的64位SHA-256> `
  --expected-origin=https://sales.example.com `
  --service-plan=<服务保护计划JSON路径> `
  --report=.runtime/preflight/production-preflight.json
```

只有报告 `status=passed` 且 15 项检查全部通过，才可进入部署审批。检查覆盖 Node 版本、生产认证哈希与会话签名值、Secure Cookie、精确 CORS、方案写入关闭、主库和备份的 `PRAGMA quick_check`/`foreign_key_check`、备份 SHA-256、四个项目服务状态，以及无关服务隔离。任何失败均以非零退出码闭锁后续步骤，报告不回显认证哈希或会话签名值。

## 15. 后续边界

以下能力不作为 Phase 1 安全与数据基础完成标准：

- 多租户权限和角色审批流。
- PDF 或 PPT 自动导出。
- 附件上传与向量检索。
- 财务级权限、合同流和回款系统对接。
