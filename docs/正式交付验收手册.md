## 9. Phase 1 生产认证迁移

上线前先在受控终端生成密码哈希。密码只从标准输入读取，不得作为命令行参数、环境变量明文或文档内容出现：

```powershell
npm --prefix backend run auth:hash
```

将输出的 scrypt 哈希写入生产环境的 `AUTH_PASSWORD_HASH`，并完成以下生产配置：

```text
NODE_ENV=production
AUTH_ACCOUNT=<正式账号>
AUTH_PASSWORD_HASH=<auth:hash 输出>
AUTH_SESSION_SECRET=<独立生成的高强度随机值>
AUTH_COOKIE_SECURE=true
CORS_ALLOWED_ORIGINS=https://<正式业务域名>
```

迁移要求：

- 生产环境删除兼容用的明文 `AUTH_PASSWORD`，缺少哈希、会话密钥、Secure Cookie 或明确 CORS 来源时必须启动失败。
- `AUTH_SESSION_SECRET` 与模型密钥分开保存，轮换前先安排所有现有会话重新登录。
- 登录响应只创建七天有效的 `HttpOnly`、`Secure`、`SameSite=Lax` Cookie，前端存储中不保存会话值或 CSRF 值。
- 浏览器写操作必须携带 `X-CSRF-Token`；用户接口不得使用 `Authorization: Bearer`。
- 周报导出允许 `?format=word`，但 URL 不得包含 `query token`、授权值或会话值。
- `CORS_ALLOWED_ORIGINS` 只列正式 HTTPS 来源，不使用通配符，不把开发地址带入生产配置。

## 10. 数据库检查、备份与恢复

升级前先停止本项目服务并确认数据库离线。只允许停止 `sentelligent` 项目所属服务，不得结束机器上的全部 Node 进程。

```powershell
npm run wsl:stack:stop
npm --prefix backend run db:check
npm run wsl:db:info
npm run wsl:db:backup -- --label=phase1-complete
```

必须归档以下证据：

- `db:check` 与 `wsl:db:info` 均为 ready。
- `PRAGMA quick_check` 返回 `ok`。
- `PRAGMA foreign_key_check` 返回零行。
- 12 张既有业务表的记录数，以及 `schema_migrations` 中每个版本和 checksum。
- 备份文件绝对路径、字节数和 `SHA-256`；可在 WSL 使用 `sha256sum <备份路径>` 复核。
- 备份文件不进入 Git，不与 `.env`、日志或会话 Cookie 一起归档。

先对独立临时数据库做恢复演练，禁止直接覆盖在线数据库：

```powershell
npm run wsl:db:restore -- --database-url=/tmp/sentelligent-phase1-restore-test.sqlite --backup-path=<备份绝对路径>
npm run wsl:db:info -- --database-url=/tmp/sentelligent-phase1-restore-test.sqlite
```

恢复演练必须再次通过 `PRAGMA quick_check`、`PRAGMA foreign_key_check`、12 张业务表计数和迁移 checksum 比对。正式恢复时先停止本项目后端，确认无 `-wal`、`-shm` 或打开连接，再执行：

```powershell
npm run wsl:db:restore -- --backup-path=<已验真的备份绝对路径>
npm run wsl:db:info
npm run wsl:stack:start
npm run wsl:stack:health
```

恢复过程会先验证候选库，再原子替换并保留恢复前副本；任何校验失败都不得替换现有数据库。

## 11. Cookie、CSRF 与 CORS 验收

本地浏览器集成 QA 使用随机端口，并仅对该回环进程设置 `AUTH_COOKIE_SECURE=false`、`NODE_ENV=test` 和精确的 `CORS_ALLOWED_ORIGINS`。生产始终保持 `AUTH_COOKIE_SECURE=true`。

验收证据必须同时证明：

- 登录响应有七天 `HttpOnly` Cookie，响应体和浏览器存储都没有 Bearer token。
- 刷新页面通过 `GET /api/auth/session` 恢复登录，不依赖 localStorage。
- `POST`、`PATCH`、`DELETE` 请求有 `X-CSRF-Token`，没有 `Authorization` 请求头。
- 周报导出由带 Cookie 的 fetch 完成，URL 没有 query token。
- 退出调用 `POST /api/auth/logout`；旧 Cookie 再访问会得到 401，受保护界面回到登录页。
- 只有 `CORS_ALLOWED_ORIGINS` 中的来源获得 credentialed CORS 响应。

执行：

```powershell
npm --prefix outputs/product-design-prototype run qa:integration
```

## 12. 服务归属与应用回滚

所有服务单元、PID 文件、运行目录和日志目录必须带 `sentelligent` 项目标识。操作前先确认实际服务名和命令行归属：

```bash
systemctl list-unit-files 'sentelligent*'
systemctl status sentelligent-backend.service sentelligent-frontend.service
systemctl status sentelligent-caddy.service sentelligent-weixin-agent.service
```

禁止按进程名批量结束全部 Node、停止整台主机的容器栈或重启无关 systemd 服务。本项目脚本只可根据已记录 PID，并在命令行、工作目录和运行时指纹匹配后终止进程。

应用回滚步骤：

1. 只停止 `sentelligent-backend.service`、`sentelligent-frontend.service` 和 `sentelligent-weixin-agent.service`，保留当前 release 目录、数据库备份及其 SHA-256；共享 Caddy 不随应用回滚重启。
2. 将 backend、frontend、weixin-agent 三份 systemd unit 的 `ExecStart` 和 `WorkingDirectory` 重新固定到上一已验收 immutable release 的真实路径，执行 `systemctl daemon-reload`；`current` 只作人工标记，不构成回滚。
3. Phase 1 数据库迁移采用加法迁移；回滚前确认旧应用能忽略新增表和新增列，不能兼容时停止回滚并使用向前修复。
4. 只重启三个项目服务，核对实际 `ExecStart`、`WorkingDirectory` 和项目 Node 24 后，再执行健康检查、登录、查询、写入、周报导出和审计抽查。
5. 只有在应用回滚仍无法恢复且已完成恢复演练时，才按第 10 节离线恢复数据库。

数据库 schema 不做破坏性回滚。应用回滚与数据恢复是两个独立审批动作，不能在同一条自动命令中隐式完成。

## 13. 便携发布包

发布包必须从真实 Git 仓库中已经提交且工作树完全干净的发布候选提交生成。脚本始终从源仓库自行读取 commit 和 clean 状态，不接受 CLI `--allow-dirty`、API `allowDirty` 或调用者提供的 `gitInfo` 元数据覆盖；当前分支或 detached 状态不参与归档身份。打包器会为该完整 commit 创建独立 detached 临时 worktree，在其中删除并重新生成产品前端 `dist`，再从 Git blob 读取 tracked 源文件、从这次临时构建读取前端产物。当前工作区中被 Git 忽略的旧 `dist` 永远不作为归档输入。先按锁文件安装依赖并完成前端质量门和发布专项测试：

```powershell
npm ci --prefix outputs/product-design-prototype
npm --prefix outputs/product-design-prototype run build
npm run test:release
npm run release:package -- --output-dir=.runtime/releases
```

命令中的第一次前端构建属于质量门；`release:package` 仍会在 exact-commit 临时 worktree 中再次构建，以建立发布产物与 manifest 所声明 commit 的强绑定。临时构建只允许改动 `outputs/product-design-prototype/dist`，若构建脚本改动或生成其他待提交文件则失败关闭；临时 worktree 无论成功或失败都必须清理。

`release:package` 是本地离线脚本，不连接服务器、不读取生产环境文件，也不执行部署。默认生成标准 `tar.gz`，并在命令输出中给出归档绝对路径和归档 SHA-256。归档根目录内的 `release-manifest.json` 必须包含：

- 完整 Git commit 和工作树 clean 状态。
- `outputs/product-design-prototype/dist` 每个构建文件的 SHA-256。
- `backend/src/db/migrations` 每个迁移文件的 SHA-256。
- 除产品前端 `dist` 和 manifest 自身外，每个源文件的 SHA-256，以及按路径稳定排序计算的 source tree SHA-256。
- 生产必需环境变量名称，不包含任何变量值。
- 将三个项目 systemd unit 重新固定到目标 immutable release 真实路径的应用回滚步骤，以及数据库只允许前向迁移的边界。

发布包强制排除：

- `.env` 和生产环境文件；必须保留不含密钥的 `*.env.example` 配置模板。
- SQLite 数据库、sidecar、`.sqlite.bak`、`.db.backup` 等备份或副本。
- 日志、轮转日志、PID、轮转 PID、voice recordings、voice assets、runtime audio 和 session 目录。
- `node_modules`、包缓存、build、coverage、非产品 dist 和临时目录；必须保留可部署的 `outputs/product-design-prototype/dist`。
- `.git`、`.codex`、`.runtime`、`.worktrees` 和代理运行元数据。
- 私钥、私密凭据文件和已有压缩归档。

归档创建前必须对全部待打包文本执行内容级密钥门禁，`*.env.example` 以及文件名带 `example`、`sample`、`template` 的凭据或配置模板也必须扫描，不能因“示例文件”跳过。门禁按 BOM 正确解码 UTF-8、UTF-16LE、UTF-16BE；明确文本或配置扩展名无法可靠解码、出现异常 NUL 时必须失败关闭。敏感赋值字段覆盖 YAML、JSON、env 及其他文本中的 quoted/unquoted 值，并统一识别 camelCase、snake_case、kebab-case 的 password、accessToken、clientSecret、apiKey、privateKey 等名称。空值、`${ENV_NAME}`、`<set-in-production>`、`your-token-here` 等明确占位值允许保留；非空真实 secret、key、token、password、private-key，`sk-` 等高风险 provider key、Bearer token 和私钥头必须拒绝。失败信息只记录文件、行号和规则名，不回显命中的值；门禁通过前不得写出 archive。

生成后必须解压到独立临时目录验证，不得直接覆盖当前项目：

```powershell
$archive = (Get-ChildItem .runtime\releases\*.tar.gz | Sort-Object LastWriteTime -Descending | Select-Object -First 1).FullName
$extract = Join-Path $env:TEMP "sentelligent-release-verify"
New-Item -ItemType Directory -Force $extract | Out-Null
tar -xzf $archive -C $extract
Get-ChildItem $extract -Recurse -Force
```

核对 manifest 的完整 commit 与标签解析出的 commit、`git rev-parse HEAD` 一致，并复算归档、构建、迁移、逐文件 source hash 和 source tree hash。分支名或 detached 状态不参与归档身份。测试会显式放入一个被 Git 忽略的旧 `dist`，证明归档只包含 exact-commit 临时 worktree 的新构建；除 fixture 外，还会在带中文的源根、输出和解压目录中从候选 commit 重建真实前端并实际解压，临时 worktree、源目录、archive 与解压目录在 `finally` 中清理。

部署前基线与部署后验收必须分开采集和留档：

- 首次部署 immutable release 前，线上仍可使用 legacy 直路径 `/opt/sentelligent-sales-workbench/<固定入口>`；预检必须能以该真实现场生成可信部署前基线。

- 不得用计划中的 `current`/release 路径冒充部署前 legacy 现场，也不得沿用部署前快照作为部署后验收证据。

`projectServices` 必须精确包含且只能包含 `sentelligent-backend.service`、`sentelligent-frontend.service`、`sentelligent-caddy.service`、`sentelligent-weixin-agent.service` 四项，额外的 `sentelligent-*` 伪服务同样拒绝。四项服务都必须完整盘点并验证 `FragmentPath`、`ExecStart`、`User`、`WorkingDirectory`、active 和 enabled。便携 legacy 配置继续允许 `/usr/bin/node` 与 `root`/`sentelligent`；当前 CentOS 7 部署只允许 `sentzx` 使用 `/usr/local/bin/node` 运行三个精确 legacy 入口。新 release 必须改用 `/opt/sentelligent-sales-workbench/runtime/node-v24/bin/node` 并直接引用 immutable release 真实路径，不能使用共享的 `/usr/local/bin/node` 或 `current`。shell、外部脚本、额外参数、命令控制符、相邻项目根、固定入口的子路径或后缀均拒绝。

backend 与 weixin-agent 必须在服务快照中同时记录 `EnvironmentFile` 和 `EnvironmentFileSha256`。两项都要指向传给 `--env-file` 的同一真实文件，SHA-256 必须与预检现场复算结果完全一致；frontend 和共享 Caddy 不读取该业务环境文件。`DATABASE_URL` 必须在环境文件中显式配置，并与 `--database` 指向同一个真实文件或同一文件身份，不能依赖相对路径漂移、符号链接替换或手工复制的另一份数据库。

当前服务器的 `sentelligent-caddy.service` 是共享 Caddy，仅作为保护清单核验：允许 `caddy` 用户、空 `WorkingDirectory` 和 `/usr/local/bin/caddy run --config /etc/caddy/Caddyfile`。无论服务快照呈现何种 legacy 配置，部署计划中的 `start`、`stop`、`restart`、`enable` 变更动作都不得包含 sentelligent-caddy.service；只读的 `status`、`is-active`、`is-enabled` 可用于核验。

`projectPaths` 不是调用者可扩展的白名单：必须包含项目根和精确 Caddy 配置路径，其他条目只能位于项目根的 `current` 或 `releases` 分支内，任意根外路径或项目根下其他自定义分支均拒绝。将所有权字段替换为服务器只读盘点结果时，不要把无关服务改名或声明为项目路径。`plannedCommands` 只接受单一项目服务的 `systemctl start/stop/restart/enable/status/is-active/is-enabled`，并要求与 `plannedActions` 一一对应；共享 Caddy 的变更动作会被拒绝。服务名不能由 `projectServices` 输入扩展。`service`、用户级 systemd、多个服务、sudo、shell 运算符、`pkill`、`killall`、批量结束 Node 和停止整套 Compose 栈均会被拒绝。预检脚本只解析这些字符串，不执行其中任何命令。

主库可以是在线只读检查时带 `-wal`/`-shm` 的 SQLite 数据库，预检仍执行 `quick_check` 和 `foreign_key_check`；备份必须是无 sidecar 的独立一致文件。`databasePath` 与 `backupPath` 必须取得可靠 realpath 和非零 dev/ino，既要解析为不同路径，也要验证不是同一个文件、符号链接目标或硬链接。任一 realpath/stat 调用失败或 dev/ino 缺失、为零、不可靠时，`backup.identity` 必须失败关闭，不能仅凭路径字符串不同放行。

### 15.3 验收数据清理边界

- 首选做法是在独立数据库副本上完成真实样本验收。停止该隔离实例后删除整套测试数据库及其 `-wal`、`-shm`，再确认正式数据库的文件身份和 SHA-256 未变化；源样本目录不得清理。
- 费用和发票的界面“删除”是软删除，相关审计仍会保留；微信“拒绝关联”会将状态改为 `rejected` 并保留原件。这些操作不等于物理清理。
- `backend/scripts/icost-acceptance-cleanup.mjs` 只删除一条由 `ACCEPTANCE-<UUID>` 标记、且与 server-local exact manifest 完全一致的 iCost 验收数据。它不接受按文本、日期或金额模糊匹配，也不处理微信待处理记录、手工付款附件、发票或任意浏览器测试数据。
- iCost 清理前必须先做离线备份，并在服务器本地使用私有环境文件和权限受限的 manifest；不得通过 HTTP 暴露清理接口。命令只写占位路径：

```powershell
node --env-file=<private-backend-env-path> backend/scripts/icost-acceptance-cleanup.mjs `
  --manifest=<server-local-acceptance-manifest.json>
```

- 清理报告必须为 `status=clean`，精确删除计数与 manifest 一致，残留计数全为零，`PRAGMA quick_check` 为 `ok` 且 `foreign_key_check` 为零行。任一归属、数据库身份、依赖关系或计数不一致时中止，不得扩大删除范围。
- 当前没有针对微信待处理、手工附件和发票的通用硬删除工具。若这些样本已写入生产，应将其视为正式留存数据；需要物理删除时另行设计并审计精确清理方案，不能直接执行临时 SQL。
