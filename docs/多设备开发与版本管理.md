# 多设备开发与版本管理

## 1. 新设备准备

安装：

- Git
- GitHub CLI `gh`
- Node.js 24 和 npm
- Chrome
- Codex（需要使用时）

确认：

```bash
git --version
gh auth status
node --version
npm --version
```

Node 主版本必须是 24。不要用旧 Node 生成 lockfile 或发布包。

## 2. 获取代码

```bash
git clone https://github.com/jiangjz9986-cloud/sentelligent-sales-workbench.git
cd sentelligent-sales-workbench
git fetch --tags --prune
git switch main
git pull --ff-only origin main
```

安装依赖：

```bash
npm ci --prefix backend
npm ci --prefix outputs/product-design-prototype
```

根目录没有第三方运行依赖，不需要执行根目录 `npm install`。

## 3. 配置本机环境

从示例创建本机文件：

```text
backend/.env.example -> backend/.env
outputs/product-design-prototype/.env.example -> outputs/product-design-prototype/.env.local
```

真实账号、密码、DeepSeek Key、高德 Key、微信状态、SSH 私钥和生产环境文件通过私下安全渠道转移。不要发到 Issue、PR、Commit、Codex 任务描述或聊天截图中。

每台设备单独配置 `.env`。GitHub 只提供示例字段和占位值。

## 4. 每个任务使用独立分支和 worktree

```bash
git fetch origin
git worktree add .worktrees/<topic> -b codex/<topic> origin/main
cd .worktrees/<topic>
```

一个 Codex 任务只负责一个清晰范围。不同任务不要共享未提交文件，也不要让两个任务同时修改同一大型页面。

提交前：

```bash
git status -sb
git diff --check
npm run scan:secrets
```

## 5. 本地启动和验证

```bash
npm run dev:start
npm run dev:health
```

最小门禁：

```bash
npm run test:deploy
npm --prefix backend test
npm --prefix outputs/product-design-prototype run qa:local
```

跨模块、登录、AI、语音、地图、数据库或部署改动还要运行：

```bash
npm --prefix outputs/product-design-prototype run qa:integration
```

完成后停止本地服务：

```bash
npm run dev:stop
```

## 6. 设备之间交接

离开当前设备前：

1. 确认所有需要保留的代码已经提交。
2. 推送分支并创建 Draft PR。
3. 在 PR 中写清修改文件、测试结果、截图、数据库影响和剩余问题。
4. 不用网盘拷贝整个工作区；`node_modules`、`.runtime`、数据库和日志不能跨设备混用。

在另一台设备继续：

```bash
git fetch origin --prune --tags
git switch <branch>
git pull --ff-only
npm ci --prefix backend
npm ci --prefix outputs/product-design-prototype
```

先读 PR、`CHANGELOG.md`、`docs/开发进度与路线图.md` 和相关实现计划，再继续修改。

## 7. 合并规则

- `main` 只接收通过 CI 和实际验收的 PR。
- 不直接 force-push `main`。
- 不把多个无关需求塞进同一个 PR。
- 数据库迁移保持向前兼容，应用回滚不能依赖 schema 降级。
- 合并后删除远端临时分支；需要继续开发时从新的 `origin/main` 创建 worktree。

## 8. 版本规则

版本同时写入：

- `VERSION`
- 根 `package.json`
- `backend/package.json` 与 lockfile
- 前端 `package.json` 与 lockfile
- `CHANGELOG.md`
- `docs/releases/vX.Y.Z.md`

正式发布步骤：

```bash
git switch main
git pull --ff-only origin main
git tag -a vX.Y.Z -m "森特智行 vX.Y.Z"
git push origin vX.Y.Z
```

标签推送后，GitHub Actions 会重新验证项目、生成不可变归档和 SHA-256，并创建 GitHub Release。标签不能移动或复用；修复必须发布新版本。

## 9. 版本时间

以下时间必须使用 ISO 8601：

- 内容冻结时间
- Git commit 时间
- Git tag 创建时间
- GitHub Release `publishedAt`
- 生产部署开始和完成时间
- 备份生成时间
- 预检和冒烟完成时间
- 回滚开始和完成时间

GitHub Release 与服务器 evidence 是最终时间记录，文档不能预填尚未发生的成功结果。
