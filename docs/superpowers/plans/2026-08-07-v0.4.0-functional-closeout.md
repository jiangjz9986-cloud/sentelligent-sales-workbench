# v0.4.0 Functional Closeout Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use test-driven-development for every behavior change, systematic-debugging for existing failures, and verification-before-completion before release. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the remaining v0.4.0 reimbursement gaps: deterministic release-package tests, OCR/DeepSeek payment-proof intake with a real human-review path, stable expense references throughout the UI and exports, and print-safe authenticated PDF payment proofs.

**Architecture:** Keep raw payment screenshots and PDFs inside the existing lossless document store. Extract text locally, send only text to a payment-proof-specific DeepSeek analyzer, persist recognition evidence separately from typed hints, and never auto-attach OCR/AI-only results. Reuse the existing authenticated PDF.js Canvas component for print rendering, and propagate `referenceCode` through the shared contract and every reimbursement output.

**Tech Stack:** Node.js 24, `node:test`, SQLite, local Tesseract/Poppler adapters, DeepSeek OpenAI-compatible chat completions, React 19, Vite 6, PDF.js, Playwright Chromium/WebKit.

- [x] **Step 2: Define the recognizer contract**

Implement:

```js
export async function recognizePaymentProofDocument(file, options = {}) {
  return {
    extractedText,
    evidence: { amountCents, occurredOn, paidTime, merchant, paymentMethod },
    typedEvidence,
    conflicts,
    confidence,
    warnings,
    source: { provider, model },
  };
}
```

Only `amountCents`, `occurredOn`, `paidTime`, optional `merchant/paymentMethod`, `confidence`, and warnings are accepted from the model.

- [x] **Step 3: Recognize outside the database transaction**

In `POST /api/travel-expense-document-inbox`, claim idempotency first. For a new claim, run recognition before `withImmediateTransaction`; for a replay, return the stored response without calling OCR or DeepSeek again.

- [x] **Step 4: Fail closed on conflicts and AI-only evidence**

Preserve the existing compatible behavior for an explicit `EXP-...` plus complete typed evidence. Any OCR/model-derived evidence, or any typed/recognized conflict, creates a `review_required` inbox record and candidates but never an attachment.

- [x] **Step 5: Verify original-file retention on recognition failure**

When OCR/PDF extraction or model analysis fails, store the original losslessly, record only a stable warning/error code, never expose command paths/provider bodies, and return `202` with a recoverable review state.
