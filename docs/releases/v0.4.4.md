# Sentelligent v0.4.4

This patch release prevents reasoning-capable DeepSeek sales-decision responses from exhausting the completion budget before the required `sales-decision-v1` JSON is emitted. It does not change travel-reimbursement behavior, business APIs, database migrations, dependencies, authentication, or user-facing workflows.

## Root cause and pre-release evidence

- Before v0.4.4, the deployed v0.4.3 release passed cutover and both `24/24` production preflights, but two fixed HTTPS smoke runs each finished `24/25`; the only failed check was `sales-decision.create`, and both runs physically cleaned all test data.
- The provider returned HTTP 200 and valid outer JSON, but `message.content` was empty, causing the existing safe `mock_model_fallback` path.
- A server-local diagnostic used an isolated temporary database and the exact smoke context without writing production business data. With an enforced `3000`-token limit it returned `finish_reason=length`, exactly `3000` completion tokens, and no standard content.
- The same context completed with `finish_reason=stop`, valid JSON, a valid `sales-decision-v1` contract, and `source=deepseek` while consuming `6946` completion tokens under a `12000` limit.
- Diagnostic reports contain only response-shape metadata and counts. They do not contain provider credentials, model text, login material, database contents, or business attachments.

## Changes

- Raise only the sales-decision model request `max_tokens` value from `6400` to `12000`.
- Add a regression assertion for the combined reasoning and structured-JSON token budget.
- Keep the two-minute minimum model timeout and the production smoke request timeout unchanged.
- Keep deterministic fallback and all evidence, stage, compliance, score, stakeholder, and human-confirmed writeback guardrails unchanged.

## Deployment boundary (fulfilled)

- v0.4.4 was published from the exact merged `main` commit and deployed as a new root-owned immutable release; the v0.4.3 release tree was not modified.
- A fresh consistent SQLite backup, service plan, and exact `24/24` preflight were generated within the required freshness window.
- Only `sentelligent-backend.service`, `sentelligent-frontend.service`, and `sentelligent-weixin-agent.service` were stopped/restarted.
- Shared Caddy, Qingyang, account-vault, Mihomo, and protected ports were unchanged before and after cutover.
- Post-cutover `24/24`, HTTPS smoke `25/25` with `cleanup=clean`, and real Chrome desktop/mobile acceptance passed; details are in [部署记录](../部署记录.md).
