# 森特智行 v0.6.21 小小备注与微信引用回执热修

## 问题

- 图片识别出的商户被同时写入备注，导致新草稿的备注不是空值。
- 微信界面显示引用回复，但本次 provider 更新没有把引用元数据投影到后端；同时存在多笔待确认时，后端返回业务 409，远程适配器又把它包装成“处理消息失败”。
- 微信发送接口可能以 HTTP 2xx 空正文表示成功。旧实现要求 JSON 正文，因此消息已在手机可见时仍把 outbox 标成失败并重试。

## 修复合同

- 新草稿的 `note` 默认为空；`merchant` 和 `purpose` 保持独立，空备注在固定消息中显示“无”。
- 用户明确修改备注后，数据库行、分析 JSON、不可变修订和下一版待确认消息保持一致。
- provider 的 HTTP 2xx 空/空白发送回执视为成功；非空回执仍严格要求合法 JSON 对象且所有出现的状态字段为数值零。
- 引用消息若含 `sentelligent:<64hex>` 客户端标识，则优先使用该稳定 outbox 身份；普通入站消息自己的幂等身份仍保持 provider `message_id` 优先。
- 只有结构严格受限的 409 `clarify/review_required/error` 正文可以返回微信；其他非 2xx 继续按传输失败处理。
- provider 丢失引用元数据时，明确的备注修改可落到唯一草稿，或十五分钟内更新且比次新草稿至少新一小时的最新草稿。确认或取消还必须具有最新 outbox 已成功送达证据；时间相近的多笔草稿继续要求精确引用。
- 隐式草稿选择完成后再次校验绑定 owner、精确发送者与本人私聊，其他 allowlist 发送者和允许群聊均不能修改、确认或取消财务草稿。

## 验收与边界

- 回归覆盖备注默认空、紧凑自然语言修改、分析快照一致、空 HTTP 回执、稳定引用客户端标识、旧版引用拒绝、受限 409 回传、缺失引用时的多草稿隔离及跨发送者/群聊拒绝。
- 不批量改写既有待确认记录，避免把用户手工备注误判为旧自动备注。
- 图片与 PDF 继续使用 `deepseek-v4-flash-vision-exp`；其他模型任务继续使用 `deepseek-v4-flash`。
- 无数据库迁移；只切换 backend、frontend 和 weixin-agent，不重启共享 Caddy。
- 使用本地 exact-commit 不可变制品直接发布生产，不同步 GitHub。
