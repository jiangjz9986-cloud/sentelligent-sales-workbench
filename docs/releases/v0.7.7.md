# 森特智行 v0.7.7 每日晨报 + 周五收尾包（v0.7 系列收官）

## 目标

- 每日 09:00（Asia/Shanghai）小小微信晨报：今日行程 + 待办（逾期/今日/未排期）+ 活跃风险 + 昨日以来新招标，首行确定性"焦点"；周五 16:30 收尾包：周报草稿状态引用 + 凭证缺失清单 + 发票缺失清单（总蓝图 H 阶段，v0.7 系列收官版）。
- 零迁移：outbox 行即持久幂等 marker（`daily-digest:{date}` / `friday-closeout:{date}`），重启不重发、当日补发、跨日不补、worker 离线顺延。

## 主要变更

见 `CHANGELOG.md` [0.7.7] 条目。要点：新模块 `backend/src/dailyDigest/`（digestContent 取数组装 / digestMessage fail-closed 渲染 / digestScheduler 独立 60s 循环）、`listNotices` 扩 `firstSeenFrom`、`outboxRepository.hasKey` 只读点查、`renderOutboxMessage` 增 `daily_digest`/`friday_closeout` 两分支、`GET /api/digest/status` + `POST /api/digest/run`（dryRun 预览/手动补发两分支）、`DAILY_DIGEST_*` 四配置键、审计三 action（actor=system:daily-digest）。

## 关键裁定（施工图 2026-08-28-v076-daily-digest-design.md，文件名 v076 为版本顺延前旧编号）

- 独立调度循环（不共用 v0.7.5 待办提醒 tick）：提醒是数据驱动扫描、晨报是时刻驱动，开关独立（`DAILY_DIGEST_AUTO_RUN` 生产默认开）、失败面隔离；三个调度器（招标/提醒/晨报）同构不同容。
- 幂等键一天一键不含内容哈希（同一天不允许第二条，内容随补发时刻漂移属预期）；`hasKey` 点查 + enqueue 同键异内容 409 反向保证 marker 强一致。
- 周报段只读引用不自动落库：Web 落库路径有模型副作用与人工 knowledgeIds 判断，系统代发会污染审计语义；用户要全文发"销售周报"、要落库去 Web 周报页。
- 晨报四段全空不发（宁静优先，audit skipped 留痕）；收尾包全空也发（"确认无欠账"是周五收尾的核心信息）。
- 发票缺失取 `unacknowledgedMissingCents > 0`（已确认"无票"的费用周五不再催）——与 Web 合计条徽标的 `invoice_pending` 状态数口径不同：微信收尾包催"未确认的缺口"，Web 徽标显示"发票状态为待补"的笔数，两者数字可能不同属预期。凭证缺失与 Web `paymentProofMissingCount` 完全同口径（无任何 payment_proof 附件）。

## 实施说明（与设计的偏差）

- ① 命名对齐现场指令：payload kind `weekly_wrapup` → `friday_closeout`；幂等键 `weekly-wrapup:{weekStart}` → `friday-closeout:{date}`（date=当周五业务日，手动补发在非周五也归一到本周五日期，一周一键语义不变）；审计 `digest.weekly_wrapup.sent` → `digest.friday.sent`；端点 `/api/assistant/digest/*` → `/api/digest/*`；配置统一 `DAILY_DIGEST_*` 前缀（`WEEKLY_WRAPUP_TIME` → `DAILY_DIGEST_FRIDAY_TIME`）。
- ② 设计"F 延期时待办段降级路径"作废不用：迁移 0028 与 actionItemStore 已上线，晨报待办段直接用 `remind_at` 判窗。
- ③ 设计第四章招标 lenient 单条容错**不实施**（现场裁定降级）：2026-08-20 陈账已于 v0.7.6 部署核验确认自愈（采集器连续 success、last_error=null、配置修复 AUTO_RUN=true）。观察项：如未来再现"单条坏公告整批拒绝"（症状为 scheduler `lastError="医院招标快照校验失败"` 持续），按施工图 §4.3 加固（sync lenient + internalRunner + scheduler 消费三件）。
- ④ 时刻配置解析失败按仓库 config 惯例 fail-fast 抛错（设计写"回默认"）；解析器接受自身输出以保持 loadConfig 幂等（服务器入口把已加载 config 回喂 createServer，对象值二次解析必须原样通过——实施中实测发现并修复）。
- ⑤ 设计引用的 adapter 内部函数 `riskRows` 非导出面，落地用导出的 `actionRiskSummary().risks`；行程"损坏 plan"因 DB 有 `json_valid` CHECK 不可能是非法 JSON，fail-open 判定改为"stops 非非空数组即仅显示标题"。
- ⑥ `resolveBusinessOwner` 无法解析（绑定账号 ≠ 配置 owner）按瞬态处理：不入队不标记不审计、下 tick 重试（设计未细化；误发"已齐 ✓"比迟发更糟）。
