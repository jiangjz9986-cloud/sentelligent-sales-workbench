# 发布与回滚操作手册

## 1. 原则

- 发布来源必须是已合并的 `origin/main` 和唯一正式 tag。
- 每个版本解压到新的不可变目录，禁止覆盖旧 release。
- 数据、备份、录音、微信状态和生产配置位于 release 之外。
- 只操作 backend、frontend、weixin-agent 三个项目服务。
- `sentelligent-caddy.service` 是共享服务，只做状态和配置哈希核验。
- systemd 直接固定到真实 release 路径；不能只切换 `current` 就认为服务已更新。

## 2. GitHub 发布

```bash
git fetch origin --tags --prune
git switch --detach origin/main
git status --porcelain
git rev-parse HEAD
```

工作树必须干净。确认 `VERSION` 和 tag 一致后推送 `vX.Y.Z`。GitHub Release workflow 会执行：

1. Node.js 24 依赖安装。
2. 发布脚本、安全扫描、后端测试和前端 `qa:local`。
3. 不可变 `.tar.gz` 生成。
4. `release-result.json` 和 `SHA256SUMS` 生成。
5. Actions artifact 与 GitHub Release 发布。

下载后复算 SHA-256，再上传服务器。

## 3. 部署前证据

必须记录：

- tag、完整 commit、GitHub Release URL 和归档 SHA-256
- 当前 release 路径和三个项目服务的 ExecStart
- backend/weixin-agent 实际 `EnvironmentFile` 路径、文件 SHA-256 和环境中的显式 `DATABASE_URL`
- 共享 Caddy 配置 SHA-256、PID、active/enabled
- account-vault、Qingyang、Mihomo 的 active 状态
- 数据库路径、备份路径、字节数、SHA-256、`quick_check` 和外键结果
- 当前监听端口和归属

生产数据库处于 WAL 写入时，不用旧版系统 `sqlite3` 直接判定完整性。使用项目 Node.js 24 的在线一致性快照，再对快照执行检查。

## 4. 生产预检

切换前使用本版 `scripts/production-preflight.mjs` 对现网真实快照复核 `25/25`；预期 hostname 和 machine-id 必须来自独立部署清单，并与当前主机及服务快照一致。切换脚本只接受 15 分钟内生成、权限为 `0600`、SHA-256 单独复算一致，并绑定当前 release、数据库和主机的精确 `25/25` 报告。候选 release 和候选 commit 由候选 manifest 另行校验。三个项目服务固定到新 release 后，必须重新采集快照并再次复核 `25/25`。`env.assistantSecrets` 强制微信机器边界和助手确认密钥独立且具有足够熵；`env.aiModel` 强制 `model` 模式、`deepseek` provider、官方 HTTPS 端点、`deepseek-v4-flash` 和独立非空 `MODEL_API_KEY`；`release.identity` 把 manifest、完整 commit 和三个项目服务绑定到同一 immutable release；`database.environmentBinding` 把环境文件中的显式 `DATABASE_URL`、被检查数据库以及 backend/weixin-agent 的 `EnvironmentFile` 真实路径和 SHA-256 绑定到同一生产状态。任一阶段失败都停止发布或立即回滚，不允许通过修改报告、复制另一份环境文件或扩大服务白名单绕过。

旧生产 release 如果仍由运行账号拥有，必须在生成预检前执行一次只改元数据的冻结，并确认 manifest 内容哈希未变化；从该动作之后，所有 release 都必须保持 `root:root` 且运行账号不可写。冻结完成后重新执行 25/25，不能复用冻结前的报告：

```bash
current="$(readlink -f /opt/sentelligent-sales-workbench/current)"
case "$current" in
  /opt/sentelligent-sales-workbench/releases/*) ;;
  *) exit 1 ;;
esac
trusted_manifest_sha=<从已校验的GitHub-Release归档独立取得的64位SHA-256>
manifest_sha_before="$(sha256sum "$current/release-manifest.json" | awk '{print $1}')"
test "$manifest_sha_before" = "$trusted_manifest_sha"
chown -R root:root "$current"
find "$current" -type d -exec chmod go-w {} +
find "$current" -type f -exec chmod go-w {} +
manifest_sha_after="$(sha256sum "$current/release-manifest.json" | awk '{print $1}')"
test "$manifest_sha_after" = "$trusted_manifest_sha"
```

服务计划只能包含：

- `sentelligent-backend.service`
- `sentelligent-frontend.service`
- `sentelligent-caddy.service`
- `sentelligent-weixin-agent.service`

共享 Caddy 只能出现在只读核验中。禁止 `pkill`、`killall`、批量停止 Node、停止整套 Compose、用户级 systemd 或一条命令操作多个服务。

## 5. 安装 release

推荐目录：

```text
/opt/sentelligent-sales-workbench/releases/<yyyy-mm-dd>_<short-sha>
```

步骤：

1. 先用 GitHub Release 的 `SHA256SUMS` 校验归档，再去掉归档自带的单一顶层目录并解压到新的 release 根目录：

```bash
release=/opt/sentelligent-sales-workbench/releases/<yyyy-mm-dd>_<short-sha>
umask 022
install -d -o root -g root -m 0755 "$release"
tar -xzf sentelligent-sales-workbench-v<version>.tar.gz \
  -C "$release" \
  --no-same-owner \
  --no-same-permissions \
  --strip-components=1
chown -R root:root "$release"
find "$release" -type d -exec chmod go-w {} +
find "$release" -type f -exec chmod go-w {} +
test -f "$release/release-manifest.json"
```
2. 只有在 release 已冻结为 `root:root` 且运行账号不可写后，才复算 `release-manifest.json` 中的前端构建、生产依赖、迁移和源码 hash；任一结果不一致都停止部署。切换脚本也必须按“冻结 → 完整验哈希”的顺序再次验证，防止验签与冻结之间发生替换。
3. 直接使用归档内已经通过质量门的 `outputs/product-design-prototype/dist`。该目录必须由发布打包器在 manifest 所声明 commit 的 detached 临时 worktree 中重新生成；发布机当前工作区里被 Git 忽略的旧 `dist` 不得进入归档。服务器不得重新运行前端构建，也不得用本机或服务器临时构建结果覆盖该目录。
4. 直接使用归档中已按后端锁文件生成且写入 `productionDependencyHashes` 的生产依赖。服务器不得在 release 内执行 `npm ci`、上传本机 `node_modules` 或添加任何未被 manifest 逐文件哈希绑定的依赖。
5. 运行数据库迁移；迁移必须为加法和向前兼容。
6. 生成三份 systemd 单元，`ExecStart` 和 `WorkingDirectory` 写入新 release 的真实路径，不能引用 `current`；backend 与 weixin-agent 必须读取同一份 release 外生产 `EnvironmentFile`，不得把配置复制进 release。
7. 安装单元后执行 `systemctl daemon-reload`，只重启 backend、frontend、weixin-agent 三个项目服务。
8. 不停止或重启共享 Caddy。
9. 更新 `current` 作为人工标记，但服务是否生效以 `systemctl show` 显示的真实路径为准。

正式切换前复算基线报告 SHA-256，并作为 cutover 的必填门禁输入。报告必须位于项目受控 evidence 目录，不能复用超过 15 分钟的旧报告：

```bash
preflight_report=/opt/sentelligent-sales-workbench/evidence/production-preflight-<UTC>.json
preflight_sha="$(sha256sum "$preflight_report" | awk '{print $1}')"

bash "$release/scripts/production-cutover.sh" \
  --new-release="$release" \
  --expected-commit=<候选40位小写Git提交SHA> \
  --database=/var/lib/sentelligent-sales-workbench/sales-workbench.sqlite \
  --backup-dir=/opt/sentelligent-sales-workbench/backups/<cutover-id> \
  --evidence-dir=/opt/sentelligent-sales-workbench/evidence/<cutover-id> \
  --weixin-session-dir=/opt/sentelligent-sales-workbench/weixin-session \
  --node=/opt/sentelligent-sales-workbench/runtime/node-v24/bin/node \
  --preflight-report="$preflight_report" \
  --preflight-report-sha256="$preflight_sha"
```

归档缺少前端 `dist` 或其 hash 与 manifest 不一致时，必须重新生成 GitHub Release 资产；服务器现场重建不能替代发布资产。

## 6. 部署后验收

至少检查：

```text
systemctl is-active / is-enabled
systemctl show User,Group,SupplementaryGroups,DynamicUser,WorkingDirectory,ExecStart
127.0.0.1:8088 和 127.0.0.1:8897 监听
HTTP 308 跳转 HTTPS
API health
生产预检 25/25
公开 HTTPS 冒烟 25/25
线上 `outputs/product-design-prototype/dist` 与 `release-manifest.json` 的 hash 一致
最近 error 日志为空
共享 Caddy 和受保护服务仍 active
```

浏览器补测登录、快速记录默认语音、客户只读详情/修改、移动端内部滚动和横向溢出。

## 7. 应用回滚

应用回滚使用上一已验收 release，不删除失败版本和证据。

1. 记录当前失败 release、服务状态和日志。
2. 确认上一 release 的 manifest、文件和 Node 24 入口仍完整。
3. 重写或恢复 backend、frontend、weixin-agent 三份 systemd 单元，使每个 `WorkingDirectory` 和 `ExecStart` 都直接引用目标 immutable release 的真实路径，不能引用 `current`。
4. 重新加载单元并只重启三个项目服务：

```bash
systemctl daemon-reload
systemctl restart sentelligent-backend.service
systemctl restart sentelligent-frontend.service
systemctl restart sentelligent-weixin-agent.service
```

5. 运行以下命令，确认三个服务都已固定到目标 release，且 `WorkingDirectory` 和 `ExecStart` 中没有 `/current/`：

```bash
systemctl show \
  -p WorkingDirectory -p ExecStart \
  sentelligent-backend.service \
  sentelligent-frontend.service \
  sentelligent-weixin-agent.service
```

6. 更新 `current` 辅助指针。它只方便人工识别；只切换该指针不构成回滚，也不会改变正在运行的服务。
7. 重跑服务盘点、`25/25` 预检和 `25/25` 冒烟。
8. 记录回滚时间、原因、前后 commit 和验证结果。

不要重启共享 Caddy。不要删除新 release，以便复盘。

## 8. 数据库恢复

应用回滚默认不恢复数据库。数据库恢复需要单独批准，原因是迁移采用向前兼容策略，盲目恢复会丢失发布后的真实业务写入。

只有在数据库损坏且已经完成恢复演练时，才使用已校验备份：

1. 停止所有项目写入服务。
2. 再次备份当前损坏现场。
3. 校验候选备份身份、SHA-256、`quick_check` 和外键。
4. 使用项目恢复工具安装候选并保留恢复前快照。
5. 启动项目服务并完成全部生产验收。

## 9. 证据保留

每次版本保留 Git tag、GitHub Release、归档、manifest、SHA-256、数据库备份、服务前后快照、预检报告、冒烟结果和回滚点。敏感环境文件不进入 GitHub Release。
